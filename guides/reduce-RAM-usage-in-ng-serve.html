کاهش مصرف RAM در ng serve

در این پروژه، مصرف بالای حافظه عمدتاً به ترکیب SSR، source map، prebundle و اندازه‌ی graph پروژه مربوط است.

علت‌های اصلی

  • در angular.json، برای dev server گزینه‌های server، ssr و outputMode: "server" فعال هستند؛ بنابراین bundle مرورگر و سرور هر دو ساخته می‌شوند.
  • sourceMap در حالت development فعال است.
  • Angular CLI cache خاموش است و prebundle مربوط به Vite/esbuild فشار بیشتری ایجاد می‌کند.
  • پروژه حدود ۳٬۳۷۹ فایل سورس و ۱۸۸MB asset دارد.
  • PreloadAllModules بیشتر روی حافظه‌ی مرورگر اثر دارد و عامل اصلی مصرف RAM خود esbuild نیست.

۱. اولین تست پیشنهادی

ابتدا prebundle را غیرفعال کنید:

npx ng serve --configuration development --prebundle=false

این کار معمولاً مصرف process جداگانه‌ی esbuild را کاهش می‌دهد؛ در عوض startup و بعضی rebuildها ممکن است کمی کندتر شوند.

۲. فعال کردن cache

در angular.json، تنظیم cache را به شکل زیر تغییر دهید:

"cli": {
    "analytics": false,
    "cache": {
        "enabled": true,
        "environment": "local"
    }
}

cache مستقیماً سقف RAM را تعیین نمی‌کند، اما باعث می‌شود prebundle و buildهای تکراری دوباره از ابتدا انجام نشوند.

۳. راه‌حل مؤثرتر: target توسعه‌ی CSR

برای کار روزمره یک target جداگانه‌ی client-only بسازید و در آن این گزینه‌ها را حذف کنید:

"server": "src/main.server.ts",
"ssr": {
    "entry": "src/server.ts"
},
"outputMode": "server"

سپس توسعه‌ی معمول را با target سبک‌تر اجرا کنید:

npx ng run main-web-application:serve-client

در این حالت process سرور Angular و بخش مهمی از graph مربوط به SSR ساخته نمی‌شود. برای تست SSR می‌توانید همچنان از target فعلی استفاده کنید.

۴. محدود کردن heap Node

NODE_OPTIONS=--max-old-space-size=1536 \
npx ng serve --prebundle=false
این گزینه فقط heap مربوط به Node را محدود می‌کند؛ esbuild ممکن است حافظه‌ی native جداگانه مصرف کند. مقدار کم می‌تواند باعث خطای OOM شود، بنابراین این روش راه‌حل اصلی نیست.

ترتیب پیشنهادی اجرا

  1. --prebundle=false را تست کنید.
  2. Angular CLI cache را فعال کنید.
  3. برای توسعه target مخصوص CSR اضافه کنید.
  4. فقط در صورت نیاز max-old-space-size تعیین کنید.
جمع‌بندی: برای این پروژه، ساختن dev target بدون SSR بیشترین کاهش مصرف RAM را ایجاد می‌کند؛ خاموش کردن prebundle سریع‌ترین تست کم‌ریسک برای شروع است.
